# Technology audit: what a native macOS culling app can use or integrate in 2026 (RawLine Selects)

Scope note: research done 8 Nov 2026 with about 20 search/fetch calls. Where a claim comes from my prior knowledge of Apple/vendor APIs and not from a source fetched in this session, it sits under **Inferences** and is marked "(unverified this session)". The spec's principles shape every verdict: local-only AI that shows *where to look* and never *what to keep*, XMP sidecars only, Lightroom keyboard. So features like aesthetic scores are rated for whether they can be used **without judging**, not just whether they exist.

Rating legend used in the tables: Maturity (GA = shipping and stable, New = shipped in the last OS cycle, Beta = only in betas/macOS 27), Difficulty (L = days, M = 1-3 weeks, H = a month or more / research).

## 1. Apple frameworks (Vision, Core ML/MLX/Foundation Models, Core Image RAW, Metal, ImageIO, AVFoundation, EDR, Spotlight/Quick Look, App Intents, Sidecar, external drives)

### Takeaway
Everything the spec's section 5.1 needs (faces, landmarks, saliency, horizon, feature prints, image registration) is shipping Vision API on macOS 15. The 2026 news is (a) **RAW 9** in Core Image, a Core ML demosaic/denoise model on the Neural Engine, opt-in, macOS 27 only and heavier than RAW 8; and (b) **image input for the Foundation Models on-device LLM** (WWDC26, OS 27 cycle). Vision's aesthetics request exists since macOS 15 but conflicts with the "never judge" principle. Use it, if at all, only internally (e.g. to pick a burst *cover thumbnail*), never shown as a score.

### Cited Findings
- `VNCalculateImageAestheticsScoresRequest` / `CalculateImageAestheticsScoresRequest` is available from macOS 15.0. It returns `VNImageAestheticsScoresObservation` with `overallScore` (range [-1, 1]; combines aesthetic score, a failure score and the utility label) and `isUtility` (flags images such as screenshots/receipts that are "not necessarily poor quality but may lack memorable content") — [Apple doc: CalculateImageAestheticsScoresRequest](https://developer.apple.com/documentation/vision/calculateimageaestheticsscoresrequest.md); [Apple doc: isUtility](https://developer.apple.com/tutorials/data/documentation/vision/vnimageaestheticsscoresobservation/isutility.md); [Create with Swift tutorial](https://createwithswift.com/scoring-the-aesthetics-of-an-image-with-the-vision-framework)
- Developers report negative `overallScore` values and ask Apple to confirm the range. No official answer found. A beta-era report said the simulator returned the same score for every image — [Apple Dev Forums thread 781561](https://developer.apple.com/forums/thread/781561); [Apple Dev Forums thread 757286](https://developer.apple.com/forums/thread/757286)
- WWDC25 (OS 26) added `DetectLensSmudgeRequest` (confidence 0–1 that the image is smudged; used by the iOS 26 Camera app) and `RecognizeDocumentsRequest` (structured text, tables, lists, barcodes, 26 languages). The session lists macOS among supported platforms — [WWDC25 session 272](https://developer.apple.com/videos/play/wwdc2025/272/); [Kodeco: new Vision features iOS 18–26](https://www.kodeco.com/ios/programs/apple-intelligence/apple-ai-models/49307523-vision-framework/04-unveiling-new-vision-framework-features-in-ios-18-ios-26/05); [WWDC Notes 272](https://wwdcnotes.com/documentation/wwdc25-272-read-documents-using-the-vision-framework/)
- **RAW 9 (WWDC26 session 305):** a tiled Core ML model for demosaic and denoise. It runs on the Apple Neural Engine, is *not* on by default (check `supportedDecoderVersions` contains `version9`, set `decoderVersion = .version9`), and `supportedCameraModels` lists the cameras per version. It is more compute- and memory-intensive and runs the model "hundreds of times per image". `colorNoiseReductionAmount`, `detailAmount` and `moireReductionAmount` do not apply. Advice: `scaleFactor` for reduced-size display, one `CIContext` per view with `cacheIntermediates = true`, the Extended Virtual Addressing entitlement for more cache, render into MTKView. Exports use `cacheIntermediates = false` and `memoryLimit` 512–1024 MB. Availability: iOS/iPadOS/macOS/visionOS **27**. Apple RAW support has grown to 784 camera models, and the list grows through OTA updates — [WWDC26 session 305 "RAW 9 in Core Image"](https://developer.apple.com/videos/play/wwdc2026/305/); [PetaPixel, 10 Jun 2026](https://petapixel.com/2026/06/10/apples-raw-processing-is-finally-evolving-after-a-decade-and-its-a-big-deal/)
- An Apple DTS engineer confirmed a performance cost for the new processing. Separate forum threads report CIRAWFilter slowing down after opening several different images, and ask about `decoderVersion` scope and `linearSpaceFilter` ordering — [Forum: CIRAWFilter decoderVersion scope and RAW 9](https://developer.apple.com/forums/thread/834485); [Forum: CIRAWFilter slows down after a few images](https://developer.apple.com/forums/thread/851397?answerId=909825022); [Forum thread 810339](https://developer.apple.com/forums/thread/810339)
- `CIRAWFilter` (class API since macOS 12) exposes `previewImage` (the embedded preview) and `linearSpaceFilter` (a hook to insert your own filter in linear scene space before tone mapping) — [Apple doc: CIRAWFilter](https://developer.apple.com/documentation/coreimage/cirawfilter.md); [Apple doc: RAW image options](https://developer.apple.com/documentation/coreimage/raw-image-options.md)
- **Foundation Models framework:** launched with macOS 26 as text-only at first. WWDC26 added multimodal prompts that accept NSImage/CGImage/CIImage/CVPixelBuffer/file URLs, plus Vision-backed built-in tools (OCR, barcode). Developer tests of image input ran on Xcode 27 beta / OS 27 betas. Secondary sources disagree on whether image input reaches macOS 26.x — [Apple WWDC26 ML guide](https://developer.apple.com/wwdc26/guides/machine-learning/); [Apple: Foundation Models framework](https://developer.apple.com/foundation-models-framework/); [Classmethod: multimodal image analysis test](https://dev.classmethod.jp/en/articles/foundation-models-multimodal-image-analysis/); [DEV: What's new in Foundation Models at WWDC26](https://dev.to/hariharanjagan/whats-new-in-apples-foundation-models-framework-at-wwdc-2026-5227); [WWDC26 session 241](https://developer.apple.com/videos/play/wwdc2026/241)
- WWDC22 "Display EDR content with Core Image, Metal, and SwiftUI" is still Apple's reference path for EDR display of RAW-derived images (cited by the RAW 9 session) — [WWDC26 session 305](https://developer.apple.com/videos/play/wwdc2026/305/)

## 2. Camera metadata (Sony MakerNotes AF/focus/face/burst/shutter count; Canon/Nikon/Fuji; ExifTool/LibRaw/Exiv2 licensing; how others read AF points)

### Takeaway
The Sony focus point lives in `Sony:FocusLocation` (int16u[4]/[5]-style values: image width, height, then x, y). Recent bodies add `FocusFrameSize` and `FocusPosition2`, but the field layout is only community-documented and inconsistent across sources. FastRawViewer deliberately does **not** show AF points because the tags are undocumented. digiKam and Adobe Camera Raw do, with partial Sony coverage. Burst/sequence data (`ReleaseMode2`, `SequenceNumber`) and `ShutterCount` (mechanical only on A1 II) are exposed by ExifTool. Licensing pushes toward a native Swift parser: Exiv2 is GPL-2.0-only, LibRaw is LGPL-2.1/CDDL, and ExifTool is Perl (Artistic/GPL), usable only as a bundled external process.

### Cited Findings
- digiKam's Sony focus extractor reads only `FocusLocation` from ExifTool's `MakerNotes.Sony.Camera` group: `af[0]`,`af[1]` = image width/height, `af[3]`,`af[4]` = focus x/y (index 2 unused). It normalises x/y by width/height. Point size uses a factor the source calls "a guess". If there are fewer than 5 values it logs "Unsupported Sony Camera" and falls back to generic EXIF. File licence GPL-2.0-or-later — [digiKam focuspoints_extractor_sony.cpp](https://lxr.kde.org/source/graphics/digikam/core/libs/metadataengine/focuspoint/focuspoints_extractor_sony.cpp)
- A KDE bug for the a6700 shows some bodies have "FocusLocation with less than 5 entries" plus `FocusFrameSize` and `FocusPosition2`. Fixed in digiKam 8.5.0 — [KDE Bug 490330](https://bugs.kde.org/show_bug.cgi?id=490330)
- ExifTool forum: A7 IV users see four-number `FocusLocation` values and suspect face/eye/subject coordinates; meaning not confirmed. Another thread proposes a new Sony tag for focus position from the image plane — [ExifTool forum: focus area A7 IV](https://exiftool.org/forum/index.php?msg=77145); [ExifTool forum: new Sony focus position entry](https://exiftool.org/forum/index.php?msg=85376)
- `FocusFrameSize` is sometimes "n/a" and sometimes a value like 416x417 in A7 IV sample dumps (not always populated) — [Imaging Resource A7 IV EXIF DSC01347](https://old.imaging-resource.com/PRODS/sony-a7-iv/EXIF/Y-WB-A7IV_PROTO-DSC01347.HTM); [Imaging Resource A7 IV EXIF DSC01148](https://old.imaging-resource.com/PRODS/sony-a7-iv/EXIF/Y-WB-A7IV_PROTO-DSC01148.HTM)
- RawCull, a macOS culling project, has a native Sony MakerNote parser covering the A1 and A9 III. It notes the A9 III stores its TIFF data near the end of the file. Its description of the FocusLocation layout differs from the forum reading (pages returned 404 when fetched this session; known only from search snippets) — [RawCull blog: Sony MakerNote parser (search snippet)](https://rawcull.netlify.app/blog/2026/03/25/sony-makernote-parser)

## 3. Sharpness and blur measurement (classic algorithms, local models, burst ranking without auto-selecting)

### Takeaway
No new sources were fetched for this area this session, so everything is inference from established practice. The safe, principle-compatible path is a **GPU sharpness heatmap / focus peaking** computed on the embedded JPEG, shown only on demand, plus "sharpness *at the AF point*" used only to *order the flicker/compare view*, never to pick or reject.

### Cited Findings
- FastRawViewer users have asked for "focus point as option for culling for sharpness", showing demand for AF-region sharpness — [FastRawViewer forum node 826](https://www.fastrawviewer.com/node/826)
- Metal rendering path and CIContext practice for interactive RAW display is Apple's recommendation (relevant if peaking runs on RAW) — [WWDC26 session 305](https://developer.apple.com/videos/play/wwdc2026/305/)

### Inferences
- **Laplacian variance** (variance of a 3×3 Laplacian), **Tenengrad** (Sobel gradient energy) and **FFT high-frequency ratio** are the standard no-reference focus measures. On Apple Silicon, Laplacian + per-tile variance on a 24–60 MP texture via MPS is millisecond-scale. Being tile-based (e.g. 32×32 px tiles) gives a heatmap, and the tile under the AF box gives a local value (unverified this session).
- **Embedded JPEG vs RAW:** Sony's embedded preview is camera-sharpened and compressed, which inflates gradient metrics and creates JPEG-block artefacts at 8×8. Relative comparisons *within a burst* (same body, same settings) remain valid. Absolute thresholds across shoots do not. Use RAW (CIRAWFilter with sharpening at zero) only when a user explicitly checks critical focus.
- **Peaking display:** Sobel magnitude → threshold → coloured overlay on a CALayer/Metal layer, with a user-set threshold. This is a "you judge" tool and fits the principle.
- **Open-source local models (licences need checking before use):** blur detection CNNs (e.g. DeblurGAN discriminators, "blur detection" Laplacian-CNN repos) are mostly research code with mixed licences. Eye-state classifiers built on MediaPipe Face Mesh (Apache-2.0) eye-aspect-ratio exist. The spec explicitly excludes "eyes closed" warnings, so these are out of scope. One permitted use: an *eye crop strip* sorted by face position, not by eye state.
- **Burst ranking without auto-selecting:** compute AF-region sharpness per frame and offer "sort this burst by local detail" only as an *ordering* for the compare/flicker view, with no badge and no rejection. Alternatively, only use it to pre-position the flicker pair. This sits on the edge of "judging", so Andrea must decide. The spec currently says no sharpness rankings, which would exclude even this.
- Statistics (spec 5.6, "focus statistics per lens"): AF-region sharpness aggregated per lens is a diagnostic, not a judgement on a photo. Good candidate.

### Gaps
- No benchmark sources fetched for MPS Laplacian on M-series; no current list of permissively licensed blur/eye-state models was verified this session.

## 4. Metadata standards (XMP rating/label/pick, IPTC 2025.1 incl. AI fields, C2PA, keywording, Photo Mechanic code replacements, GPX geotagging)

### Takeaway
`xmp:Rating`, `xmp:Label` and Lightroom's `xmpDM:pick` (-1/0/1, since LrC 13.2 Feb 2024) are the core fields. Pick handling is community-documented, not in Adobe docs, and has known bugs. IPTC 2025.1 (Oct/Nov 2025) added four AI fields that a culling app only needs to *preserve*, not write. C2PA has an Apache/MIT Swift SDK (macOS 14+) but signing belongs to the export app, not to a sidecar-only culler.

### Cited Findings
- Lightroom Classic reads and writes `xmpDM:pick` ("-1", "0", "1") and `xmpDM:good` ("true"/"false") per ExifTool's author. Unflagged is written as 0. Adobe docs mention only `xmpDM:good` — [ExifTool forum: New Adobe Lightroom XMP fields](https://exiftool.org/forum/index.php?msg=85176); [ExifTool forum msg 85488](https://exiftool.org/forum/index.php?msg=85488)
- Adobe 13.2 release note: "Flags in XMP – When reading metadata from and writing metadata to the files, Lightroom now includes flags", primarily for compatibility with Lightroom Desktop; not supported by Bridge — [Lightroom Killer Tips: Feb 2024 update](https://lightroomkillertips.com/lightroom-classic-and-lightroom-february-update/); [Adobe Community: LrC 13.2 and flags in XMP](https://community.adobe.com/t5/lightroom-classic-discussions/lrc-v13-2-and-flags-in-xmp/m-p/14440118)

## 7. All manufacturers: containers, embedded previews, AF/burst MakerNotes, Apple RAW coverage (added on user request: support every brand, not only Sony)

### Takeaway
The embedded-preview-first design already used for Sony is the key to supporting every brand. It **decouples culling from Apple's RAW decoder**, which lags new bodies and excludes some compressions (Sony A7 V non-lossless, OM High Res, Nikon HE until 26.4 per community reports). It also gives speed. But preview size is very uneven. **Full-size JPEG previews:** Canon CR3 (trak1), Sony, and probably most Nikon/Pentax DSLR/Z bodies. **Reduced, often around 1920 px:** Fujifilm RAF (1920×1280 on X-T1; recent bodies unverified), Panasonic, Olympus/OM. **Small or variable:** medium format (Hasselblad 3FR/FFF, Phase One IIQ) and drones. For these, 100% focus checks need a real RAW decode (CIRAWFilter, tile around the zoom point), so the app needs a per-file "preview is too small → decode RAW for zoom" path. AF data exists for Canon, Nikon, Fuji, OM, Panasonic and Pentax in documented-by-ExifTool MakerNote tags. It is absent or meaningless for medium format, drones and most DNG-only bodies.

Design consequences for RawLine Selects:
- **Per-maker preview extractors in `MediaPreview`:** TIFF walker (Sony, Nikon, Canon CR2, Panasonic, OM, Pentax, DNG, 3FR), BMFF box walker (CR3, HEIC), RAF header reader. All are small and share the existing TIFF parser. Fall back to `CGImageSourceCreateThumbnailAtIndex` and then `CIRAWFilter.previewImage`. Apple's ImageIO can still return an embedded thumbnail for many unsupported RAW bodies, but not reliably for all (unverified).
- **Preview-resolution flag:** at index time, store the preview pixel size versus sensor size. If the preview is below ~50% linear resolution (Fuji, Panasonic, OM, medium format, drones), the `Z` 100% zoom should decode a RAW tile with CIRAWFilter in the XPC service, and the UI must say "RAW zoom" while it loads. Without this the 100% view lies, which is exactly FastRawViewer's main argument against preview culling.
- **Decoder coverage watchdog:** check `CIRAWFilter.supportedCameraModels` (and decode success) at runtime. If a body is unsupported, cull on the preview only and show "RAW preview not available on this macOS version". Never fail to open the file.
- **AF overlay rollout order** (by market share for working pros and by documentation quality): Sony → Canon (AFInfo2/3) → Nikon Z (AFInfo2) → Fujifilm (FocusPixel) → OM/Panasonic → Pentax. Medium format and drones: none. Each body needs a validated sample set; unvalidated bodies get the "AF not available" badge rather than a guessed box (FastRawViewer's caution about undocumented tags applies to every maker).
- **Burst grouping:** maker sequence tags (Sony `SequenceNumber`, Fuji `SequenceNumber`, Panasonic `SequenceNumber`/`BurstMode`, Canon/Nikon drive mode) should *refine* the time-gap rule in spec 4.4, not replace it, because many bodies don't write a reliable sequence id. Canon CR3 RAW burst/roll files hold many frames in one file and need a dedicated frame-extraction path.
- **Twins and sidecars:** Fujifilm, OM and Panasonic shooters often shoot RAW+JPEG with film simulation / art filters. The JPEG twin may be the better full-size preview for culling than the small embedded one. `TwinGroup` should prefer the twin JPEG as the display source when the embedded preview is small.
- **Test corpus:** spec 4.9 already calls for real files of every brand. Raw sample sources such as raw.pixls.us (CC0 samples) and Imaging Resource sample galleries cover most current bodies (raw.pixls.us licence and coverage unverified this session).
